# 发射观礼行程延期时的组合保障与选择权估值

窗口变化时核对观礼及普通游线的可选权利和实际费用，并在同一窗口情景下比较新一季延期条款、
执行已经卖出去的换行程权利。

## 资料和运行环境

`data/` 提供本地合成业务资料。各业务文件为 UTF-8 JSON 数组，键、单位和关联见 [资料字典](data/README.md)。`format.json` 记录列集合和基础引用约束。

使用 Python 3.11。在普通 Python 环境可用 `python3 -m pip install -r requirements.txt` 安装锁定的分析依赖。检查提供的资料可运行：

```sh
python3 -m unittest discover -s tests -v
```

资料检查覆盖文件可读性、字段与明确的单列引用。业务原始记录允许保留冲突、未决关系及尚未到达的观察。

## 工具

`launch_window` 在资料之上提供可复算的时间线、分配、条款比较与执行记录。所有命令默认读 `data/`，可用
`--data` 指向其它同结构目录。

```sh
python3 -m launch_window audit                       # 资料审计：明确冲突与未决关系
python3 -m launch_window timeline --as-of 2026-08-14 # 按当时已知信息重演
python3 -m launch_window compare --delays 0,1,2 --leads 0,1
python3 -m launch_window reserve --terms 灵活 --delays 0,1,2
python3 -m launch_window risk --delays 2 --lead 0 --open
python3 -m launch_window execute --event L24 --as-of 2026-08-14
python3 -m launch_window register --event L24 --as-of 2026-08-14 --terms 灵活
python3 -m launch_window impact --event L24 --booking B2407 --as-of 2026-08-14
python3 -m launch_window commit --event L24 --as-of 2026-08-14
python3 -m launch_window behavior --as-of 2026-08-14
python3 -m launch_window costs --terms 灵活 --delay 2
python3 -m launch_window attribution
```

## 口径

**时间可见性。** 任何时点只使用 `known <= as_of` 的通告和 `day <= as_of` 的旅客回复。晚发的通告、
晚到的回复一律不可见；重做试算不能反过来替客服释放仍然有效的承诺。

**三类权利分开。**
- 可以先售的权利：原售日的观礼票、按订单约定可独立锁定的普通游线。
- 通告明确后才发出的换期选项：改到新的观礼日，必须已有确认通告且通知提前量满足条款
  `min_notice`。观礼日未唯一确定时不给任何观礼选项。
- 需要退费的部分：以上都不能兑现时按合同人均退费。

**同窗口核对各条产品。** 条款比较固定同一组 `(延期天数, 通知提前量, 窗口是否已确认)`，
逐条产品在同一实际窗口下求解，不让每条产品挑自己最能接住的日期。

**互斥窗口共享预留。** 候选实际日互斥：同一资源键按各窗口需求取最大值。同一窗口内不同客群
可能同时接受，需求先相加，不按客群取大。`reserve` 会给出共享预留与“逐窗口简单相加”的差额，
差额就是被双算的部分。

**容量只有一个份。** 同一观礼批次内同日同车组、同接待区只有一份人数上限，多个产品同时引用时仍共用。
订单不可拆，整单一起安置。优先次序按 `(既有订单, priority)` 逐档字典序：优先号小者先拿到紧张的
观礼席；既有订单在任何情况下先于新订单。

**可改期比例按销售组分层。** 估计只用同一销售组、同一优先/保留方式/可接受产品分层的历史回复；
无回复样本的层只报 0~1 边界并标 `no_evidence`，不把普通散客或其它销售组的改期率套给观礼团。
`behavior` 同时给出 Wilson 区间和样本量。

**风险边界。** 下界＝窗口落在该延期日、全部可服务旅客都接受且容量足够；上界＝截至 `as_of` 未应答的
旅客全部按合同退费。窗口未唯一确定时，不能把某一个可能日当作已确认，`risk --open` 分别对每个可能日
求边界再取最不利值。退费准备金按批核对，跨批缺口不能相互挪用。

**执行已发出的承诺。** 已接受锁定并优先兑现；已发未答继续占用容量，直到旅客回复、明确拒绝、已锁定
另一条替代，或回复时限已到并显式执行合同释放（`execute --release-expired`）。已发出的承诺与新预案撞量时，
先兑现已发权益；实在做不到的逐条列出具体冲突和仍可保留的替代，不用总体预计退款率抹平。

**事后回看。** `attribution` 把已结算成本拆成：
- 窗口变化造成：忽略容量、只看窗口本身是否让订单无法留在原计划；
- 容量被提前发完造成：按真实优先次序与容量求解后的增量；
- 已结算承诺中无法按承诺兑现的部分（承诺观礼日不是最终确认日、接受了本不可接受的产品）单独计数。

## 模块

| 模块 | 作用 |
| --- | --- |
| `model.py` | 装载资料、时间线、资源上限、资料审计 |
| `allocate.py` | 不可拆订单的容量可行分配；共享上限；忽略容量对照 |
| `behavior.py` | 按销售组分层的历史选择估计与重演 |
| `scenarios.py` | 同窗口跨条款比较、共享预留、风险边界、成本分布 |
| `ledger.py` | 已发承诺台账与执行 |
| `service.py` | 客服通告登记、可告知选项查询、发出影响与承诺顺序模拟 |
| `attribution.py` | 事后成本拆分 |

## 资料里明确可见的问题

`audit` 会列出资料自身的冲突。当前合成资料中值得注意的有：

- 若干「改到观礼」的已结算承诺，承诺日不是该批最终确认日（延期 0/1/2 天时都有出现）；
- 18 笔「同意普通游线」的订单，其 `fallback` 为空，即接受了订单不在可接受范围内的产品；
- `L24` 的 `O1` 在观礼日尚未唯一确定时发出了观礼选项；`O4` 的 `游线晚` 不在该订单可接受产品内；
- `L14`、`L24` 尚未确认实际观礼日；
- 三份条款的 `max_refund` 都低于单批全额退费敞口（2300~3450 元/批）。
